# Mewepak CMS 开发方案

**目标仓库：** ColorPrintingFactory/mewepak  
**方案日期：** 2026-11-17  
**目标技术栈：** GitHub、Cloudflare Workers / Static Assets、Supabase

## 1. 项目目标与边界

以客户现有网站作为前台视觉与功能目标，独立开发新的公开网站和管理后台，后端使用 Supabase，部署在 Cloudflare。新站的开发语言和框架不受 WordPress 限制；WordPress 备份只作为现有外观、交互、内容和媒体素材的参考。

这是产品展示与询价网站，不开发购物车、结账、支付和订单管理。前台保留产品详情与 Request a Quote 入口。

原站的图片、视频、Logo、3D 模型和文案默认全部沿用：不擅自换图、生成新素材或改写文案。迁移时可以调整文件存放位置和引用地址；只有文件格式或尺寸确实不兼容时才做必要转换，原素材内容保持不变。备份里找不到的素材先列出来确认，不自行替换。

## 2. 已核对的现状

- 备份中包含当前 mewepak-fse 网站，约有 57 个已发布页面、11 篇文章和 3 个已发布产品。主题代码仅供核对当前页面外观与行为，不要求新站继续使用。
- 产品菜单有 12 个分类：Pouch Formats 下 9 个，Specialty Packaging 下 3 个。Supabase 已预置这 12 个分类。
- 当前 /booking/ 的预约流程包含日期/时段选择、时区选项、15/30 分钟会议选项、联系人与公司信息、Video Call / Factory Visit，以及客户回执和管理员通知邮件。新站保留这些用户可见的能力，不依赖原 WordPress 插件。
- 当前 3D 预览使用 Three.js 与 GLB 模型，访客可上传正面和背面稿件，在包装模型上实时预览，并旋转、缩放和切换背景。新站保留这些交互，不要求沿用原插件代码。
- 客户 Supabase 项目目前已有 10 张后台表，全部启用 RLS；产品分类与默认预约设置已建立。现有预约表结构还需补入预约时区、会议时长、预约页展示设置、时区选项和通知邮箱等字段，才能覆盖当前 WordPress 行为。
- 客户 Cloudflare 账号已连接，目前还没有对应的 Worker 项目。应用代码通过功能分支和 PR 开发，生产发布前使用 Workers Preview 验收。

## 3. 推荐架构

~~~mermaid
flowchart TD
  GH["GitHub：分支与 PR"] --> CF["Cloudflare Worker"]
  CF --> WEB["公开网站与 /admin"]
  CF --> API["Worker API：预约与询价"]
  WEB --> DB["Supabase：公开内容、媒体与数据库"]
  WEB --> AUTH["Supabase Auth：后台登录"]
  API --> DB
~~~

- GitHub 保存前端、后台、数据库迁移与部署配置。日常开发通过功能分支和 PR 进入预览环境。
- Cloudflare Worker 通过 Static Assets 托管公开网站与 /admin/ 后台；同一个 Worker 处理预约、询价等需要服务端密钥的 API。
- Supabase 提供 Auth、Postgres 和 Storage。公开访问只读已发布内容；预约、询价和草稿内容仅授权员工可读。
- 新前台独立选用适配 Cloudflare 的技术栈重新实现，不搬运或运行 WordPress 的 PHP、FSE 主题或插件。开发时参考现站截图与备份中的页面/素材，把页面布局、颜色、字体、间距、移动端表现和交互做成相同的用户体验。
- 公开页面保留静态 HTML 与可索引正文，动态分类、产品和文章通过 Worker 读取 Supabase 已发布内容。预约和询价由 Worker 即时处理，服务端密钥只保存在 Worker Secrets。

## 4. 后台模块与内容范围

| 模块 | 主要管理内容 | 前台呈现区域 |
| --- | --- | --- |
| 分类管理 | 分类名、URL slug、两组菜单、排序、图片、可见性、SEO | Products 下拉菜单、分类页 |
| 产品管理 | 产品说明、规格、材料、印刷、应用、主图和图库、SEO、精选状态 | 产品列表与产品详情；不显示价格/购买入口 |
| 页面管理 | 页面标题、slug、页面类型、结构化内容、发布状态、SEO | 首页及 57 个现有页面 |
| 文章管理 | 标题、摘要、正文、封面、发布时间、SEO | Blog 列表与文章页 |
| 媒体库 | 图片、PDF、GLB 模型、替代文本与文件 URL | 页面、产品和 3D 预览 |
| 预约管理 | 预约名单、状态、时区、时长、客户资料、邮件处理 | /booking/ |
| 预约设置 | 工作日、时段、容量、提前天数、时区、时长、展示文案和通知邮箱 | 预约日历与预约说明 |
| 3D 资源管理 | GLB、海报图、产品关联、模型查看器参数 | 现有交互式包装预览 |
| 询价管理 | 联系人、公司、产品、联系方式、留言、跟进状态 | Request a Quote 表单 |
| 站点设置 | 联系方式、导航及共享前台配置 | Header、Footer 和全局模块 |

新 CMS 的页面内容结构按 Mewepak 的业务需求设计，不复制 WordPress 的 post type 或区块结构。页面编辑使用受控的内容区块，不允许未经清理的任意脚本直接发布到前台。

## 5. 分阶段实施

### 阶段 0：资产与页面盘点

- 对照备份和线上页面，整理页面路径、桌面/手机截图、导航、视觉样式、交互行为，以及原有文案、图片、视频、Logo 和 3D 模型素材清单。
- 记录预约、询价和 3D 预览在前台出现的位置与用户操作步骤，作为新站的功能验收标准。
- 交付：页面与功能清单、视觉验收清单、原文案/素材清单、缺失文件清单和待确认事项。

**完成标准：** 页面与特殊功能有明确的迁移路径；不存在未登记的短代码或关键外部依赖。

### 阶段 1：后台与权限

- 在目标仓库建立新站应用结构、预览/生产配置和数据库迁移版本；内容表按新 CMS 业务模型定义。
- 完成员工登录、角色授权、分类/产品/页面/文章/媒体/站点设置管理。
- 补齐预约设置与预约记录所需字段；预约写入在数据库事务中再次核对时段容量。
- 上传只允许必要的媒体格式和大小；服务端密钥只存 Cloudflare 加密变量，不下发浏览器。

**完成标准：** admin/editor 权限可区分；RLS 拒绝匿名访问草稿、预约、询价与后台设置；后台操作只写 Supabase。

| 角色 | 权限 |
| --- | --- |
| admin | 全部模块、预约设置与客户请求；后续负责邀请员工 |
| editor | 分类、产品、页面、文章、媒体和 3D 资源；不读取预约/询价个人信息，不管理员工和密钥 |

### 阶段 2：导入现有内容

- 导入 12 个产品分类、3 个已发布产品、57 个页面和 11 篇文章。
- 原样保留现有标题、正文、按钮文案、SEO 文案、图片、视频、Logo 和模型文件；保留原 slug、发布时间和发布状态。
- 图片和模型迁入 Supabase Storage 或新站媒体存储后，只更新文件引用地址，不替换素材内容；除非用户之后明确要求，不重写或润色原文案。
- 按新 CMS 的业务数据结构保存导入内容，不复制 WordPress 的内部代码结构；前台由新站独立实现。

**完成标准：** 内容数量核对一致；URL 与 SEO 字段抽查通过；原图片无断链。

### 阶段 3：新前台实现

- 按现站外观和原有素材重新实现 header、footer、菜单、首页、分类页、产品详情、Blog、预约页和通用内容页；实现方式由新技术栈决定。
- 用 Supabase 提供产品、分类、页面、文章和媒体内容；业务字段按新 CMS 设计，不要求与 WP 字段或组件一一对应。
- 保留访客熟悉的页面路径、导航层级、搜索行为、按钮行为、SEO 信息和 sitemap。
- 使用 Cloudflare 预览地址与现站截图逐页对比桌面和手机表现，达到验收标准后再安排线上切换。

**完成标准：** 新站页面在导航、布局、字体、颜色、原有图片与文案、交互和移动布局上达到现站的视觉/功能目标；不要求代码结构与 WordPress 一致；前台无商品价格、购物车或结账流程。

### 阶段 4：预约功能迁移

- 保持 /booking/ 路径、两步式交互、时区选择、会议时长、Video Call / Factory Visit 及成功提示。
- 将现有工作日、起止时间、预约容量、可提前天数、时区列表、标题/地点/头像和通知邮箱迁入 Supabase 设置。
- 预约 API 验证输入与 Turnstile；服务端再次检查可预约日期和剩余容量，防止并发超额预约。
- 迁移管理员通知、客户回执，以及现有插件在预约被确认为 Confirmed 时发送的确认邮件；取消邮件不属于当前插件行为，是否新增需单独确认。

**完成标准：** 可用时段与管理设置一致；同一满额时段不会被并发重复预订；客户与管理员邮件均能收到；预约资料不公开。

### 阶段 5：3D 预览迁移

- 以当前 3D 预览为功能目标，使用适合新前端的查看器实现旋转、缩放、正反面稿件实时贴图和背景切换；接入现有 GLB 模型资源。
- 将模型文件、海报、产品关联和视图参数改为后台管理；模型需明确正面/背面网格命名或配置。
- 默认仅在浏览器内处理访客上传的设计稿；如果未来要保存稿件，再另行设计用户授权和存储期限。

**完成标准：** 当前 3D 模型正常加载；前后稿件贴图方向正确；桌面与手机可交互；模型失败时有明确提示且不影响页面其他内容。

### 阶段 6：验收、预览与切换

- 按页面清单检查路径、菜单、产品、媒体、SEO、移动端、询价、预约和 3D 交互。
- 验证未登录/非员工不能读取或修改后台数据；检查请求体限制、输入验证、CSP、安全响应头与文件权限。
- 保留 WordPress 站点和备份，先让客户审阅 Cloudflare Workers Preview；确认后再切换域名。
- 切换后观察 404、表单、日志和索引情况；如发现关键问题，回切原 WordPress 站点。

**粗略工期：** 前台与后台约 15–25 个工作日，假设现有截图/备份完整、页面类型可归并且无需新增复杂功能。阶段 0 完成后，根据页面数量、视觉细节和内容清理量重新估时。

## 6. 上线验收清单

- 所有重要页面 URL 保持不变；确需变更的旧路径建立明确的 301 跳转。
- 首页、产品菜单、分类页、产品详情、Blog、预约页、3D 预览在桌面和手机上与现有站点核对。
- 图片、Logo、视频、3D 模型和页面文案与原站素材核对一致；没有素材时先向客户确认，不擅自补图或改文案。
- 管理端创建/编辑/发布分类、产品、页面和文章后，公开站点内容能按约定流程更新。
- 购物车、价格、支付、结账功能不出现在公开网站。
- 预约时区/时长/容量及邮件行为与当前客户流程一致；并发预约不超额。
- 匿名访客无法读取预约人、询价人、草稿内容和内部设置。
- 发布前后 sitemap、canonical、标题描述、图片 alt 和主要索引 URL 保持正确。
- 有现网备份、预览验收记录和回滚操作步骤。

## 7. 当前前置事项

1. 本方案文档入库后，目标仓库仍没有应用代码；实现阶段建立功能分支并先接预览部署。
2. 客户 Cloudflare 账号尚无 Pages 项目；仓库可写后创建预览/生产 Pages 项目并配置部署变量。
3. Supabase 已完成基础表初始化；预约字段与 WordPress 当前功能的差异需在预约迁移阶段补齐。
4. 创建第一位后台管理员并设置可信 app_metadata.role=admin；关闭公开注册。
5. 上线前由客户确认预约通知邮箱、可用时区/时长及 3D 模型列表。

当前不会切换域名或改动线上 WordPress 前端。
